\section{Solidity Execution Model and Debugging Workflow}\label{sec:bg:execmodel}

Solidity smart contracts execute in the Ethereum Virtual Machine (EVM), a state-based execution environment in which program execution is driven by transactions.
Unlike conventional applications that can often be executed directly from source code within an integrated development environment (IDE), Solidity contracts typically undergo several stages before their runtime behavior can be inspected.
A conventional Solidity debugging workflow therefore involves compilation, deployment, state initialization and transaction execution, and post-execution debugging.

\smallskip
\noindent\textbf{Step 1: Compile.}
A Solidity source file is first compiled into EVM bytecode and its associated application binary interface (ABI).
Figure~\ref{fig:bg-compile} illustrates this step using Remix IDE.
The resulting bytecode constitutes the executable representation of the contract, while the ABI provides the interface through which users and other contracts invoke its externally accessible functions.

\begin{figure}[!ht]
    \centering
    \includegraphics[width=0.9\columnwidth,height=0.35\textheight,keepaspectratio]{Fig1.pdf}
    \caption{Compilation in a conventional Solidity debugging workflow.}
    \label{fig:bg-compile}
\end{figure}
\FloatBarrier

\smallskip
\noindent\textbf{Step 2: Deploy.}
Before a contract can be executed, the compiled bytecode is deployed to a blockchain or a local blockchain environment.
As illustrated in Figure~\ref{fig:bg-deploy}, deployment creates a contract instance and invokes its constructor to initialize the contract state.
The deployed contract subsequently maintains persistent state across transactions.

\begin{figure}[!ht]
    \centering
    \includegraphics[width=0.9\columnwidth,height=0.3\textheight,keepaspectratio]{Fig2.pdf}
    \caption{Contract deployment in a conventional Solidity debugging workflow.}
    \label{fig:bg-deploy}
\end{figure}
\FloatBarrier

\smallskip
\noindent\textbf{Step 3: Initialize State and Execute.}
To inspect a target function, a developer must prepare an execution state in which the function can be invoked.
This preparation may require calling other functions in advance to initialize contract state or satisfy conditions enforced by constructs such as \texttt{require}.
Once the required state has been established, the developer supplies concrete function arguments and executes the target function as a transaction.
Figure~\ref{fig:bg-execute} shows an example of this process in Remix.

\begin{figure}[!ht]
    \centering
    \includegraphics[width=0.9\columnwidth,keepaspectratio]{Fig3.pdf}
    \caption{State initialization and target-function execution in a conventional Solidity debugging workflow.}
    \label{fig:bg-execute}
\end{figure}
\FloatBarrier

\smallskip
\noindent\textbf{Step 4: Debug.}
After the target transaction has been executed, conventional Solidity debugging tools can expose its execution trace.
For example, Remix allows developers to inspect the executed transaction and step through the corresponding EVM instructions, as illustrated in Figure~\ref{fig:bg-debug}.
The debugger provides information such as the current opcode, stack and memory contents, storage values, and the relationship between bytecode instructions and source-code locations.

\begin{figure}[!ht]
    \centering
    \includegraphics[width=1.0\columnwidth,keepaspectratio]{Fig4.pdf}
    \caption{Transaction-based bytecode debugging in a conventional Solidity debugging workflow.}
    \label{fig:bg-debug}
\end{figure}
\FloatBarrier

This workflow differs fundamentally from the edit--execute--debug cycle commonly available for traditional software.
In conventional Solidity debugging, the behavior to be inspected is materialized through a concrete execution: the contract is compiled and deployed, the required state is established, concrete inputs are supplied, and the resulting transaction trace is subsequently examined.
Accordingly, the observable debugging context is closely coupled to executable artifacts, initialized contract state, and a particular transaction execution.
These characteristics become particularly relevant when debugging support is considered during source-code development, where program behavior may need to be inspected before or while a complete concrete execution context is being prepared.

\section{Numeric Logic Errors in Solidity}\label{sec:bg:nle}
Recent studies have reported a variety of numeric-related weaknesses in smart contracts~\citep{numscout,gptscan,flyinointment,exploitablebugs,defiattacks}.
Unlike failures that trigger compilation errors, runtime exceptions, or transaction reverts, some numerical defects allow a transaction to complete successfully while producing values that are inconsistent with the intended behavior of the contract.
Following prior work, we refer to such defects as \textit{numeric logic errors}.

\begin{definition}[Numeric Logic Error]
A numeric logic error is a bug that allows a transaction to complete successfully without compile-time or runtime exceptions, but violates the developer's intended relationships among numerical values during function execution.
\end{definition}

This definition emphasizes an important characteristic of numeric logic errors.
Whether a numerical computation is erroneous cannot always be determined solely from the fact that execution succeeds or from the syntactic form of the computation.
Instead, correctness depends on whether the resulting numerical relationships conform to the behavior intended by the developer.
For example, two arithmetic expressions may both be syntactically valid and execute without reverting, while only one preserves the intended relationship among balances, exchange amounts, rewards, or accounting variables.
Thus, the intended numerical relationship constitutes part of the criterion by which such program behavior is judged.

Numeric logic errors can be distinguished according to the execution scope in which they manifest.
\textit{Single-transaction errors} arise within one atomic transaction.
The relevant computations may span multiple internal or external function calls, but the behavior leading to the erroneous numerical result is contained within a single transaction.
In contrast, \textit{multiple-transaction errors} emerge only through a sequence of transactions and therefore depend on state changes accumulated across multiple function invocations.
Examples include Risky First Deposit and Price Oracle Manipulation~\citep{gptscan,exploitablebugs}, whose effects become observable only after contract state has evolved over multiple transactions.

This dissertation primarily focuses on single-transaction numeric logic errors, including cases in which a transaction crosses contract boundaries through external calls.
This scope is consistent with the development-time analysis considered throughout the dissertation: the behavior of interest is bounded by one transaction and can therefore be analyzed with respect to the source-level execution being examined.
Numeric properties that inherently span arbitrary transaction sequences require reasoning about inter-transaction dependencies and contract-level invariants and are left outside the primary scope of this work.

\textbf{Value-level errors} arise when the computation directly produces an unintended numerical value.
Typical examples include the use of an incorrect operator or identifier, precision loss caused by integer arithmetic, or an arithmetic expression whose result differs from the value intended by the developer.
The erroneous behavior is therefore observable primarily through the values produced by the computation.

\textbf{Algorithm-level errors}, in contrast, arise from the structural arrangement of operations.
Examples include executing otherwise valid operations in an incorrect order, omitting a required state update, or failing to perform a necessary procedure call.
Although their underlying cause is structural, their effect may still become observable as an unintended relationship among numerical values.

The following sections build on these characteristics of numeric logic errors to formulate the limitations of existing debugging and analysis approaches and to motivate source-level debugging with developer-authored intent for development-time analysis.

\section{Problem Definition}
\label{sec:bg:problem}

The preceding background highlights two related limitations in Solidity development.
First, conventional debugging depends on concrete transactions and bytecode execution, which limits direct inspection of program behavior during source-code development.
Second, although numeric logic errors are defined with respect to developer-intended numerical relationships, existing analysis workflows generally provide limited support for developers to directly supply such intent as an analysis criterion.
The following subsections describe these two problems in detail.

\subsection{Transaction-Dependent and Bytecode-Dependent Debugging}
\label{subsec:bg:txdependent}
Conventional Solidity debugging is tightly coupled to concrete execution.
As described in Section~\ref{sec:bg:execmodel}, a developer typically compiles the source code, deploys the resulting bytecode, prepares the required contract state, executes a transaction with concrete inputs, and then inspects the resulting execution trace.
This workflow introduces two closely related difficulties for development-time debugging.

\smallskip
\noindent\textbf{Repeated preparation of concrete execution contexts.}
A target function frequently depends on contract state that has been established before its invocation.
Consequently, debugging a particular behavior may require developers to execute additional transactions in advance to initialize balances, counters, reserves, permissions, or other state variables.

Figure~\ref{fig:state-preparation-example} shows a simple example.
The \texttt{withdraw} function contains a \texttt{require} condition that prevents execution from proceeding when the caller's balance is insufficient.
Therefore, the balance-update statement can be reached only after an appropriate balance has been established.
A developer who wants to debug this statement must first execute \texttt{deposit} to prepare the required contract state before invoking \texttt{withdraw}.
If the target source code or debugging scenario changes, this preparation may need to be repeated.
The same issue arises when developers want to inspect the behavior of a function under different input conditions.
Each concrete execution represents only one particular combination of function arguments and contract state.
Exploring alternative behaviors therefore requires additional executions with different inputs or state configurations.
This repeated preparation increases the cost of iterative debugging by requiring developers to repeatedly reconstruct concrete execution contexts.

\smallskip
\noindent\textbf{Dependence on post-execution bytecode traces.}
Detailed debugging information is generally obtained only after a transaction has been executed.
The debugger then presents the execution through EVM-level information such as opcodes, stack values, memory, storage, and source mappings.
Although this information accurately represents the executed transaction, it is derived from compiled bytecode rather than directly from the source-level program state in which the developer is reasoning.

This creates a mismatch between the level at which developers write and understand Solidity programs and the level at which conventional debugging exposes execution details.
A single Solidity statement may correspond to multiple EVM instructions, and the information relevant to a source-level variable or expression may be distributed across several low-level operations.
As a result, identifying how numerical values evolve through a source-level computation may require additional interpretation of the underlying execution trace.

These characteristics make conventional debugging inherently dependent on the availability of a complete concrete execution.
During development, however, developers may need to inspect how values can evolve before constructing every concrete transaction required to reproduce a specific behavior.
The first problem addressed in this dissertation is therefore how to provide source-level debugging information without requiring repeated transaction execution and bytecode-level tracing for each debugging scenario.

\subsection{Predefined Detection Criteria and Limited Support for Developer Intent}
\label{subsec:bg:predefined}

Static analysis, symbolic execution, fuzzing, type-based analysis, and learning-assisted approaches have been widely used to detect vulnerabilities and logic errors in smart contracts.
Many of these approaches identify suspicious behavior using criteria predefined by the analysis, such as vulnerability patterns, type constraints, arithmetic rules, inferred invariants, or previously characterized bug scenarios.

Such criteria are effective when the target defect corresponds to a property already represented by the analysis.
For example, a tool designed to detect a particular arithmetic pattern can report program locations that match that pattern, while a type-based analysis can identify operations that violate its predefined type rules.
However, numeric logic errors are defined relative to the numerical relationships intended by the developer.
Two computations may therefore both satisfy generic analysis rules while differing in whether they conform to the intended behavior of a particular contract.
In such cases, the relevant correctness criterion is contract-specific and may be known primarily to the developer.
Existing analysis workflows, however, generally provide limited support for developers to directly supply such numerical intent as an analysis criterion.
Extending the set of predefined rules or patterns can increase coverage, but it does not provide a direct mechanism for expressing contract-specific numerical intent.

The stage at which analysis is performed introduces an additional limitation.
Many existing approaches are primarily applied to complete implementations, deployed artifacts, or test executions.
In these workflows, the analysis is performed after executable program behavior has been constructed and is evaluated against criteria already defined by the tool or analysis method.
This differs from a development-time workflow in which developer-authored numerical intent can be provided together with the evolving source code and used directly as an analysis criterion.

\section{Overview of the Proposed Approach}
\label{sec:bg:approach}

To address the two limitations identified in Section~\ref{sec:bg:problem}, this dissertation combines two complementary approaches. 

\subsection{Transaction-Independent Source-Level Debugging}
\label{subsec:bg:rangebased}

To reduce the dependence on concrete transactions and bytecode-level traces, this dissertation adopts transaction-independent source-level debugging based on interval analysis.

Instead of executing a function with a single concrete input and contract state, the approach represents relevant numerical values as intervals and analyzes how these abstract values evolve through the source-level program.
For example, rather than repeatedly executing a function with several individual input values, a developer can specify a range of values of interest.
The analysis represents this range using the interval abstract domain, propagates it through the program, and derives abstract program states at relevant source-code locations.
These abstract states summarize possible numerical values without requiring a separate concrete transaction for every value represented by the interval.

This approach also changes the level at which debugging information is presented.
Rather than requiring developers to primarily inspect EVM instructions after transaction execution, program behavior can be examined in relation to source-level statements and variables.
The resulting abstract states can therefore serve as a debugging context in which developers inspect how values evolve across statements, branches, function calls, and loops.

The resulting debugging process does not reproduce a single concrete execution trace.
Instead, it summarizes a set of possible executions represented by the supplied ranges through interval-based abstract analysis.
This enables program behavior to be inspected without repeatedly preparing every corresponding concrete execution context, while retaining source-level information needed for interactive debugging.


\subsection{Development-Time Intent Validation}
\label{subsec:bg:devtime}
Transaction-independent source-level debugging provides information about how program values may evolve, but the resulting abstract states alone do not determine whether the analyzed behavior is correct.
As discussed in Section~\ref{sec:bg:nle}, numeric logic errors are defined relative to numerical relationships intended by the developer.
This dissertation therefore complements source-level debugging with a mechanism that allows developers to explicitly provide such relationships as analysis criteria.

The approach associates developer-authored numerical intent with relevant source-level program states.
Instead of relying exclusively on vulnerability patterns or other detection criteria predefined by an analysis tool, the specified intent describes relationships that the developer expects program values to satisfy.
The analysis can then evaluate the abstract program states derived through interval-based analysis against these developer-provided criteria.
Providing intent during development also allows the analysis criterion to evolve together with the source code.
Developers can specify numerical relationships relevant to the behavior currently being implemented or inspected and validate them within the same source-level analysis context used for debugging.

In this way, source-level debugging provides the program states to be inspected, while developer-authored intent provides an explicit criterion for determining whether the analyzed numerical behavior conforms to the intended behavior.

\section{Algorithm}

\begin{algorithm}[H]
\caption{Fixpoint iteration over a function CFG}\label{alg:fixpoint}
\begin{algorithmic}[1]
\Require function CFG $G=(N,E)$, initial store $\sigma_0$
\Ensure $\Store^\sharp : N \rightarrow \Intv$
  \State $W \gets \{\,n_{\mathit{entry}}\,\}$
  \While{$W \neq \emptyset$}
    \State pop $n$ from $W$
    \State $\mathit{in} \gets \bigsqcup_{p \in \mathit{pred}(n)} \mathit{out}[p]$
    \State $\mathit{out}' \gets \absem{n}(\mathit{in})$
    \If{$\mathit{out}' \not\sqsubseteq \mathit{out}[n]$}
      \State $\mathit{out}[n] \gets \mathit{out}[n] \widen \mathit{out}'$
      \State $W \gets W \cup \mathit{succ}(n)$
    \EndIf
  \EndWhile
  \State \Return $\mathit{out}$
\end{algorithmic}
\end{algorithm}
